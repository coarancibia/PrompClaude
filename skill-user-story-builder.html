Creador de Historias de Usuario

Convierte requerimientos, reglas, Figma y tickets relacionados en Historias de Usuario claras, trazables y listas para Producto, UX, Desarrollo y QA.

Nombre técnico user-story-builderUX / DocumentaciónVersión 1.0En piloto
La estructura toma como referencia el formato real usado en PRM-3445: Historia de Usuario, problema de experiencia, secciones funcionales, criterios de aceptación, reglas de negocio, assets, errores, métricas, trazabilidad y stakeholders cuando corresponda.
Vista explicativa
01

Qué hace la skill

Analiza el requerimiento antes de redactar, identifica si corresponde a HU, feature, épica o tarea técnica, y construye una HU con la profundidad necesaria sin inventar información ni forzar secciones que no aplican.

02

Qué problema resuelve

  • Evita redactar HU desde cero en cada ticket.
  • Mantiene una estructura consistente entre diseñadoras y equipos.
  • Separa criterios de aceptación de reglas de negocio.
  • Hace visibles estados, errores, dependencias y pendientes.
  • Reduce instrucciones repetidas en cada prompt de Claude.
03

Cuándo utilizarla / no

Usar

  • Crear una HU desde contexto, notas o requerimientos.
  • Ordenar información de Figma y Jira.
  • Documentar flujos con estados y casuísticas.
  • Preparar hand-off para Desarrollo y QA.

No usar

  • Para una decisión visual menor.
  • Para inventar reglas no confirmadas.
  • Para meter varias funcionalidades independientes en una sola HU.
  • Para reemplazar la revisión de Producto o UX.
04

Inputs necesarios

  • Contexto o necesidad a resolver.
  • Usuario o actor del flujo, si está definido.
  • Reglas de negocio conocidas.
  • Links de Figma y tickets Jira relacionados.
  • Estados, errores o casuísticas conocidas.
  • País, producto o flujo cuando aplique.
  • Stakeholders o métricas solo si ya existen.
05

Outputs esperados

  • COMO / QUIERO / PARA.
  • Problema de experiencia.
  • Secciones funcionales cuando el flujo lo necesita.
  • Criterios de aceptación verificables.
  • Reglas de negocio y casuísticas.
  • Assets Desktop / Mobile.
  • Estados y errores.
  • Árbol de decisión, métricas, país, trazabilidad y stakeholders cuando corresponda.
  • Pendientes por definir sin completar vacíos con supuestos.
06

Contenido base SKILL.md

El archivo descargable incluye name y description al inicio para indicar a Claude qué hace la skill y cuándo usarla. Debajo se muestra la cabecera y un resumen; descarga el archivo para obtener las instrucciones completas.

Estructura principal
---
name: user-story-builder
description: >-
  Crea, estructura y revisa historias de usuario (HU) a partir de requerimientos, notas, reglas de negocio, diseños de Figma y tickets de Jira proporcionados. Se utiliza cuando se pide redactar una HU, convertir un requerimiento en historia de usuario, definir criterios de aceptación, documentar estados y errores o revisar si una HU está completa para el handoff a Desarrollo y QA. Separa criterios, reglas y pendientes sin inventar información. No se utiliza para cambios exclusivamente visuales ni tareas técnicas sin comportamiento de usuario.
---

# user-story-builder

1. Analizar el alcance antes de redactar.
2. Redactar COMO / QUIERO / PARA.
3. Explicar el problema de experiencia.
4. Dividir por secciones funcionales solo si aporta claridad.
5. Separar criterios de aceptación de reglas de negocio.
6. Incorporar estados, errores y assets cuando existan.
7. Añadir árbol de decisión, métricas, variantes, trazabilidad y stakeholders solo cuando apliquen.
8. Marcar pendientes sin inventar información.
9. Revisar calidad antes de entregar.
10. Mantener revisión humana en decisiones de negocio y factibilidad.
07

Decisiones que requieren revisión humana

Claude estructura; el equipo decide.

  • Reglas comerciales, límites y elegibilidad.
  • Políticas de renovación o medios de pago.
  • Copy legal y métricas objetivo.
  • Priorización, responsables y factibilidad técnica.
  • Cualquier comportamiento no documentado en los insumos.

Checklist de validación

La HU explica usuario, necesidad y valor.
El problema de experiencia se entiende.
El alcance está claro.
Los criterios son verificables.
Las reglas están separadas.
Estados y errores relevantes están cubiertos.
Los links se conservan.
Las variantes por país son explícitas.
Los pendientes son visibles.
No se inventó información.
