Cómo construimos el Design System de Prime.

El foco de esta página es contar cómo fuimos creando el DS de Prime: qué orden seguimos, qué decisiones tomamos, qué buenas prácticas aparecieron en el camino y cómo lo fuimos alineando con desarrollo. Las Skills llegaron después, como apoyo para sostener y escalar ese trabajo.

La idea central
Primero construimos una base confiable. Después la automatizamos.

El valor estuvo en ordenar foundations, componentes, reglas, estados, accesibilidad y handoff antes de pensar en acelerar tareas con IA.

01 · Punto de partida

Antes de crear componentes, ordenamos el problema.

El DS de Prime no nació como una biblioteca de botones. Partimos entendiendo qué necesitábamos estandarizar para que el producto pudiera crecer sin sumar inconsistencias.

Qué revisamos primero

  • Patrones que se repetían entre flujos.
  • Colores, tipografías, espaciados e iconografía existentes.
  • Componentes duplicados o resueltos de formas distintas.
  • Estados faltantes: loading, error, disabled, empty, éxito.
  • Necesidades de desktop y mobile.

Qué queríamos evitar

  • Crear componentes desde una pantalla aislada.
  • Resolver cada caso con una excepción nueva.
  • Diseñar sin considerar cómo se implementaría.
  • Documentar el DS recién al final.
  • Depender de la memoria de una sola persona.
02 · Flujo para crear el DS de Prime

Fuimos de lo más base a lo más específico.

Este fue el orden que mejor nos funcionó para no terminar construyendo componentes antes de tener reglas claras.

03 · Buenas prácticas que nos funcionaron

El sistema se construía con reglas, no con pantallas.

Estas decisiones fueron importantes para que el DS se mantuviera consistente y pudiera conversar mejor con desarrollo.

01
Partir por foundations.

Antes de crear componentes dejamos definidos color, tipografía, espaciado, iconografía y criterios de accesibilidad.

02
Nombrar tokens por función.

Evitar nombres amarrados a una pantalla o color puntual. El token debe explicar para qué sirve, no solo qué valor tiene.

03
Crear componentes desde patrones reales.

No sumar un componente porque “podría servir”. Primero debía existir una necesidad repetida en producto.

04
Diseñar todos los estados desde el inicio.

Default, focus, hover, disabled, error, loading y éxito eran parte del componente, no un pendiente posterior.

05
Accesibilidad como definición, no como QA final.

Contraste, tamaños, foco, labels y affordance se revisaban durante la construcción del sistema.

06
Probar componentes dentro de flujos reales.

Una variante podía verse correcta aislada y fallar cuando entraba a registro, login, suscripción o cuenta.

07
No romper componentes por resolver una excepción.

Si aparecía un caso nuevo, primero revisábamos si era una variante válida o un problema puntual del flujo.

08
Documentar mientras se construía.

Uso, restricciones, estados y decisiones quedaban registradas para que diseño y desarrollo compartieran la misma referencia.

Detalle · Cómo bajábamos una decisión al sistema

De una necesidad de pantalla a una regla reusable.

Una pantalla podía gatillar una mejora, pero no definía por sí sola el sistema. La decisión pasaba por una revisión antes de convertirse en token, variante o componente.

04 · Trabajo con desarrollo

Desarrollo participaba antes del handoff final.

El objetivo era evitar llegar al final con un DS perfecto en Figma pero difícil de implementar. Las conversaciones con Dev ayudaban a validar factibilidad, reutilización y límites del sistema.

Diseño define

Reglas y experiencia

Tokens, jerarquía, estados, comportamiento, accesibilidad y criterio de uso de los componentes.

Diseño + Dev

Factibilidad y arquitectura

Qué se reutiliza, cómo se estructura en código, qué limitaciones existen y si una variante realmente conviene incorporarla al kit.

Gobernanza

Gaps y evolución

Si aparece un caso nuevo, se decide si debe vivir en el sistema o solo en el producto. Evitamos sumar excepciones sin revisar su impacto global.

05 · Después vino la automatización

Las Skills llegaron cuando el DS ya tenía reglas claras.

No usamos las Skills para inventar el sistema. Las usamos después para reutilizar criterios que ya habíamos definido: naming, auditoría, migración y construcción de componentes.

06 · Buenas prácticas al usar IA sobre el DS

La IA funciona mejor cuando el sistema ya está bien definido.

01
Primero leer, después proponer.

Las Skills funcionan mejor cuando parten del DS real del proyecto y no de supuestos genéricos.

02
Análisis y ejecución deben separarse.

Primero queremos entender qué cambiaría y por qué. La ejecución viene después de revisar.

03
La revisión humana sigue siendo parte del flujo.

Las pruebas de migración mostraron que automatizar cambios puede romper componentes. Ese riesgo quedó como regla del proceso.

04
Una Skill sirve cuando evita explicar lo mismo.

No se crea por tener IA. Se crea cuando existe una tarea frecuente, con reglas claras y un output repetible.

07 · Cómo replicaría el proceso en FF

Replicaría el método antes que los componentes.

Prime puede servir como referencia, pero FF necesita validar sus propios patrones. Lo reutilizable es el orden de trabajo y las buenas prácticas.

Framework reutilizable para un nuevo kit
01Auditar producto
02Definir foundations
03Crear tokens
04Priorizar componentes
05Validar con Dev
06Probar en flujos reales
07Documentar y gobernar
08 · Qué nos llevaríamos de Prime

El mayor aprendizaje fue el proceso, no la librería.

Un DS sano se construye con decisiones repetibles, validación temprana y gobernanza. La librería visible es solo una parte del trabajo.
