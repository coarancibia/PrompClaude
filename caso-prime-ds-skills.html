Caso real · Jumbo Prime

Del Design System a una forma de trabajar.

Esta página no muestra solo un UI Kit. Cuenta cómo fuimos conectando Figma, reglas del DS, acuerdos con desarrollo, QA UX y Skills de Claude para reducir trabajo repetitivo y mantener criterio compartido.

La idea central
El DS no termina cuando publicamos componentes.

Funciona cuando diseño y desarrollo pueden usar las mismas reglas, detectar desvíos y volver a alimentar el sistema.

01 · Qué cambió

De revisar todo a mano, a sistematizar decisiones repetidas.

Usa el switch para contar el antes y después. No es “IA reemplazando diseño”; es conocimiento de diseño pasando de estar solo en la cabeza del equipo a quedar reutilizable.

El conocimiento estaba disperso

  • El PD recordaba qué componente correspondía.
  • Los criterios se explicaban nuevamente en cada handoff.
  • QA dependía mucho de revisión manual.
  • Los hallazgos se resolvían caso a caso.

El costo era retrabajo

  • Más vueltas entre diseño y desarrollo.
  • Inconsistencias de tokens, estados o componentes.
  • Decisiones válidas que no quedaban convertidas en regla.
  • Más tiempo para revisar tareas repetitivas.

El DS se vuelve operativo

  • Tokens, componentes, estados y accesibilidad son la referencia.
  • Los acuerdos con dev se documentan y reutilizan.
  • Las Skills toman tareas repetibles de revisión.
  • El PD mantiene las decisiones que requieren criterio.

La conversación cambia

  • Menos “¿cómo era esto?” y más validación.
  • Menos rediseño accidental.
  • Más problemas encontrados antes del handoff.
  • QA retroalimenta al DS en vez de quedar como parche aislado.

03 · Qué negociábamos con desarrollo

No todo tenía el mismo nivel de flexibilidad.

Una parte clave de la implementación fue separar lo estructural de lo que sí podía adaptarse técnicamente.

Debe respetarse

Reglas del sistema

Tokens, jerarquía, uso correcto de componentes, estados, accesibilidad y comportamientos que afectan la experiencia.

Se conversa

Solución técnica

Cómo se construye internamente, limitaciones reales del front, reutilización y decisiones que no cambian la experiencia.

Vuelve al DS

Gaps y aprendizajes

Si el caso real muestra que falta una variante, estado o patrón, no se parchea silenciosamente: se evalúa como evolución del sistema.

05 · Lo que aprendimos usando IA

Automatizar no significa soltar el control.

01
Primero leer, después proponer.

Las Skills funcionan mejor cuando parten del DS real del proyecto y no de supuestos genéricos.

02
Análisis y ejecución deben separarse.

Primero queremos entender qué cambiaría y por qué. La ejecución viene después de revisar.

03
La revisión humana sigue siendo parte del flujo.

Las pruebas de migración mostraron que automatizar cambios puede romper componentes. Ese riesgo quedó como regla del proceso.

04
Una Skill sirve cuando evita explicar lo mismo.

No se crea por tener IA. Se crea cuando existe una tarea frecuente, con reglas claras y un output repetible.

06 · Cómo lo llevaría a FF

No copiaría solamente el UI Kit de Prime.

Replicaría el proceso que permitió implementarlo. Los componentes cambian; la forma de ordenar las decisiones puede mantenerse.
