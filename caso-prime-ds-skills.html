Caso real · Jumbo Prime

Cómo fuimos armando el Design System de Prime.

No fue solo armar una librería en Figma. Fuimos ordenando criterios, creando foundations y tokens, armando componentes, probándolos en flujos reales, conversando con los devs para entender cómo necesitaban recibir el DS, corrigiendo cosas que no funcionaron y después usando Skills para ayudarnos a mantener todo más ordenado.

Lo importante para contar mañana El DS lo fuimos armando entre Diseño y Dev.

La librería fue una parte. Lo más importante fue ponernos de acuerdo en cómo queríamos diseñar, construir y mantener Prime sin que cada flujo resolviera las cosas distinto.

01 · Por qué necesitábamos homologar

¿Por qué era importante tener un DS homologado?

Prime empezó a crecer harto en pantallas, estados y funcionalidades. Si no ordenábamos una base común, era muy fácil terminar haciendo lo mismo de formas distintas según el flujo.

01
Consistencia

Mismo componente, mismo comportamiento y mismas reglas en todos los flujos.

02
Escalabilidad

Crear nuevas pantallas sin volver a definir color, spacing, inputs, modales o estados desde cero.

03
Lenguaje Diseño–Dev

Que “Button / Primary / Disabled” represente lo mismo en Figma y en código.

04
Menos deuda

Evitar excepciones, estilos hardcodeados, componentes duplicados y QA repetitivo.

02 · Nuestro flujo completo

Así fue nuestro proceso de verdad.

No fue un proceso perfecto ni lineal. Varias veces tuvimos que volver atrás porque al probar algo en un flujo real, o al conversarlo con Dev, nos dábamos cuenta de que faltaba definir mejor una regla.

03 · Cómo organizamos Figma

Figma también necesitaba una estructura clara para que el DS no se volviera inmanejable.

A medida que el sistema fue creciendo, nos sirvió separar responsabilidades dentro del archivo y apoyarnos en plugins para tareas más operativas de construcción, revisión y documentación.

Buena práctica: separar Tokens y Componentes

  • Archivo / página de Tokens: foundations, variables, colores, tipografía, spacing, iconografía y decisiones semánticas.
  • Archivo / página de Componentes: componentes, variantes, estados, propiedades y ejemplos de uso.
  • Esto nos ayudó a no mezclar decisiones base con piezas de interfaz.
  • También hace más fácil encontrar qué se debe editar y reduce el riesgo de tocar algo que no corresponde.

Plugins como apoyo

  • Usamos plugins para acelerar tareas repetitivas dentro de Figma.
  • Nos ayudaron en parte de la construcción y también en la documentación del sistema.
  • Sirvieron para ordenar información, revisar consistencia y reducir trabajo manual.
  • La regla fue usarlos como apoyo: el criterio del DS seguía siendo del equipo.

04 · De valores visuales a tokens

Acá uno de los cambios más importantes fue dejar de pensar solo en el color y empezar a pensar para qué sirve.

Los tokens nos ayudaron a que Diseño y Dev hablaran el mismo idioma. En vez de decir “usa este gris”, empezamos a hablar de la función que cumplía ese color dentro del sistema.

Antes: decisión visual suelta

#F5F5F5“gris clarito del fondo”
#...“gris del ícono secundario”
1 px“borde de la card”
opacidad“estado disabled”

Después: intención semántica

bg.sunkenGraphite / 25
icon.secondaryGraphite / 200
border.cardGraphite / 50
icon.disabledGraphite / 50
Buena prácticaSemántica antes que valor.

El nombre explica la función. Si mañana cambia el color, el uso del token sigue teniendo sentido.

Buena prácticaNo crear tokens por pantalla.

Evitar nombres como “login-grey” o “card-home-border”. El token debe poder vivir fuera del flujo que lo originó.

Buena prácticaConstruir una escala consistente.

Espaciado en múltiplos de 4 px, tipografía base coherente e iconografía con tamaños definidos reducen decisiones arbitrarias.

Buena prácticaSeparar foundation de token semántico.

La paleta base entrega valores; el token semántico decide dónde y para qué se usan.

05 · Cómo construimos componentes

Un componente no era solo hacerlo bonito y listo.

Para que de verdad funcionara dentro del DS teníamos que pensar su estructura, variantes, estados, cuándo se usa, cuándo no y cómo lo iba a entender desarrollo.

01 · EstructuraAnatomía claraQué elementos son obligatorios, opcionales y qué parte puede cambiar.
02 · PropiedadesVariantes controladasTipo, tamaño, estado, icono, contenido y comportamiento sin duplicar componentes.
03 · EstadosMás que defaultHover, focus, pressed, disabled, error, loading y success cuando correspondía.
04 · ResponsiveDesktop + mobileRevisar qué cambia en ancho, tipografía, disposición y comportamiento.
05 · AccesibilidadAA desde el diseñoContraste, foco, labels, tamaño legible y affordance como parte de la definición.
06 · DocumentaciónCuándo sí / cuándo noNo basta mostrar la variante: también hay que explicar para qué caso usarla.

06 · Buenas prácticas de uso del DS

Acá aprendimos algo importante: si cada pantalla empieza a adaptar el DS a su pinta, se termina rompiendo.

Por eso no bastaba con crear componentes. También tuvimos que definir buenas prácticas para usarlos sin empezar a meter excepciones por todos lados.

OrganizaciónSeparar Tokens y Componentes.

Nos funcionó mucho mejor tener las reglas base por un lado y los componentes por otro. Hace más fácil mantener, buscar y escalar el DS.

UsoBuscar antes de crear.

Antes de dibujar algo nuevo, revisar si ya existe un componente o una variante que resuelva el caso.

UsoNo detach como solución rápida.

Si un componente no sirve, el problema se conversa. Desvincularlo para salir del paso genera deuda y pierde trazabilidad.

UsoNo inventar valores locales.

Colores, paddings, radios, borders e iconos deben venir de las reglas del sistema.

UsoEscalar el problema, no el parche.

Si el mismo problema aparece más de una vez, revisar si requiere una variante o evolución del componente.

UsoDiseñar estados completos.

No entregar solo el happy path. Error, loading, vacío, disabled y casos borde también forman parte de la experiencia.

UsoRevisión humana.

Ni una Skill ni una migración automática reemplaza la validación de contexto, negocio y experiencia.

07 · Cómo trabajamos con los Devs

Una parte súper importante fue entender cómo los Devs necesitaban que les mostráramos el DS.

Nos podía quedar perfecto para Diseño, pero si después los Devs no entendían bien las propiedades, los estados o cómo mapearlo, igual íbamos a tener problemas. Esa conversación nos hizo cambiar varias cosas de cómo entregábamos.

Lo que necesitábamos aprender de Dev

  • Cómo estructuraban componentes y variantes en código.
  • Qué propiedades necesitaban recibir claramente desde Figma.
  • Qué nombres podían mapearse mejor entre diseño y front.
  • Qué restricciones técnicas podían afectar una variante o comportamiento.
  • Qué parte del sistema debía ser reusable y qué podía quedar específica del producto.
  • Qué información faltaba en el handoff para evitar preguntas posteriores.

Cómo cambiamos nuestra entrega

  • Menos “pantalla final” y más componentes con propiedades y estados explícitos.
  • Tokens visibles y semánticos en vez de valores sueltos.
  • Comportamiento documentado, no solo apariencia.
  • Casos responsive y estados borde definidos desde diseño.
  • Conversaciones tempranas antes de cerrar una solución.
  • QA UX comparando implementación contra reglas, no solo contra una captura.
La conversación ideal pasó a ser:
Diseño¿Qué regla queremos?Experiencia, jerarquía, accesibilidad y consistencia.
Dev¿Cómo se implementa?Arquitectura, props, reutilización y restricciones.
Ambos¿Es parte del DS?Definir si es patrón reusable o excepción del flujo.
QA¿Se respetó la regla?Validar comportamiento, estados, tokens y accesibilidad.
08 · Lo que salió bien y lo que nos dio problemas

Lo que nos salió mal también nos ayudó a definir mejores prácticas.

Funcionó bien

Lo que sí nos funcionó

  • Crear foundations antes de llenar la librería de componentes.
  • Usar tokens semánticos para separar intención de valor visual.
  • Probar componentes en pantallas reales antes de considerarlos cerrados.
  • Alinear temprano con Dev en vez de resolver todo dentro de Figma.
  • Definir accesibilidad, estados y responsive como parte del componente.
  • Usar plugins en Figma para apoyar construcción y documentación sin reemplazar el criterio del equipo.
  • Usar Skills para revisar tareas repetitivas una vez que la regla ya existía.
Nos dio problemas

Lo que nos dio problemas

  • Migrar o modificar componentes automáticamente sin revisar el impacto: podía romper instancias.
  • Crear variantes para resolver una pantalla puntual y después cargar el sistema con excepciones.
  • Asumir que el naming de diseño era suficiente sin validar cómo lo interpretaba desarrollo.
  • Revisar accesibilidad o estados demasiado tarde.
  • Entregar una UI bonita sin dejar claro comportamiento, reglas o límites.
  • Usar IA para “decidir” el sistema en vez de para aplicar criterios previamente acordados.
09 · Dónde entraron las Skills

Las Skills aparecieron después, para ayudarnos con todo lo repetitivo.

Cuando ya teníamos las reglas más claras, empezamos a crear Skills para no estar repitiendo siempre las mismas revisiones. Nos ayudaron con naming, auditorías, migraciones y construcción de componentes, pero siempre con revisión humana.

10 · Lo que Dany podría reutilizar para FF

Para FF no copiaría Prime tal cual: reutilizaría el proceso.

FF puede tener otros componentes, otra identidad o incluso otra forma de trabajar. Pero todo este camino sirve para no partir de cero y, sobre todo, para evitar varios errores que nosotros ya tuvimos.

02Homologar foundationsBase visual y accesibilidad.
03Definir tokensSemántica antes de construir componentes.
04Priorizar componentesEmpezar por los de mayor uso.
05Validar con DevProps, naming, estados y arquitectura.
06Probar en flujosNo aprobar componentes solo aislados.
07Documentar usoQué sí, qué no y cómo evoluciona.
